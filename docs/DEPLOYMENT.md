# Public deployment — Render + MongoDB Atlas

The repository includes `render.yaml` for a single-origin deployment. This keeps the storefront and API on the same host, allowing secure `SameSite=Lax` HttpOnly cookies without cross-site cookie configuration.

## Required accounts and secrets

- A Render account connected to the GitHub repository.
- A MongoDB Atlas database. Use a database user with only the permissions required for this application and allow network access only from trusted sources where possible. Render outbound IP allow-listing depends on the selected plan/region; follow the provider's current networking documentation.
- A unique admin email and password (at least 16 characters).

Never commit `.env`, Atlas credentials, JWT secrets or production admin passwords.

## Deploy

1. Push the repository to a GitHub repository.
2. In Render, create a new Blueprint and select that repository. Render reads `render.yaml`.
3. Add the requested secret values: `MONGODB_URI`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`. `JWT_SECRET` is generated by the blueprint; keep it private.
4. Deploy the service. The build command installs workspace dependencies and builds `frontend/`; the Express server serves `frontend/dist` and the `/api` routes from the same origin.
5. Wait for `/api/health` to return `{"status":"ok"...}`.
6. Run the seed command once using Render's Shell/one-off command facility: `npm run seed`. This creates the first admin and sample catalogue. Do not run the seed casually against a production database; it upserts sample products and categories.
7. Open the Render service URL. Test customer registration, login, CSRF-protected mutations, cart, COD checkout, order history, admin login, product CRUD and order status transitions.
8. Add a custom domain only after the default service URL and health check work. Enable provider-managed HTTPS.

## Runtime settings

The blueprint sets Node 26.13.1, `NODE_ENV=production`, `TRUST_PROXY=true` and `COOKIE_SAME_SITE=lax`. The application uses one origin for the frontend and API. If you later split frontend and backend across different sites, revisit CORS, `SameSite=None; Secure`, CSRF and browser third-party-cookie behavior rather than copying the current settings blindly.

## Database requirement

Checkout and order cancellation use MongoDB transactions. Use MongoDB Atlas or another replica-set deployment. A standalone local MongoDB server does not support multi-document transactions.

## Costs and availability

Hosting and database plans can change. Review current pricing, sleeping/availability limits, backups and bandwidth before selecting a plan. The Blueprint currently selects Render `free` to avoid creating a paid service without explicit approval. Free services can sleep after inactivity and have resource limits. Confirm current provider pricing and limitations before deployment; do not change to a paid plan without the project owner’s approval.

## Deployment acceptance checklist

- [ ] Public URL loads over HTTPS.
- [ ] `/api/health` returns 200.
- [ ] Registration/login/logout work; session cookie is HttpOnly and Secure in production.
- [ ] A CSRF-protected POST without a valid token is rejected.
- [ ] Non-admin users receive 403 from `/api/admin/*`.
- [ ] Product prices are read from MongoDB, never trusted from browser input.
- [ ] Checkout decrements stock transactionally and rejects insufficient stock.
- [ ] Order cancellation restores stock once; terminal orders cannot be changed.
- [ ] COD order is marked paid only when Admin marks it delivered.
- [ ] Backups and restore procedure are configured.
- [ ] No secrets appear in repository, frontend bundle or logs.

## Alternative deployment: Docker-capable platforms

A root `Dockerfile` is provided for platforms that deploy containers rather than linking a Git provider directly. It builds the React app and runs the Express API from the same origin. The image uses Node 26.13.1 in both stages because `argon2` includes a native module. Configure the same runtime secrets listed above (`MONGODB_URI`, `JWT_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`) in the platform's secret manager, and expose the platform-provided `PORT`. Do not bake `.env` files or credentials into the image. MongoDB must still be a replica-set deployment for transactional checkout/cancellation. The container build has not yet been executed in this environment; treat it as an alternative deployment path pending CI verification.

## Alternative dependency/build verification

The local execution environment previously failed DNS resolution for the npm registry. The repository now includes `.github/workflows/ci.yml`, which runs dependency installation, the dependency-free Node test suite, and the Vite production build on a GitHub-hosted runner using Node 26.13.1. This moves build verification to a separate network environment rather than treating the local DNS failure as a project failure. A successful workflow run is required before enabling Render's `After CI Checks Pass` deployment policy.
