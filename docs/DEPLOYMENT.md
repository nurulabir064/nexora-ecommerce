# Public deployment — Render + MongoDB Atlas

The repository includes `render.yaml` for a single-origin deployment. This keeps the storefront and API on the same host, allowing secure `SameSite=Lax` HttpOnly cookies without cross-site cookie configuration.

## Required accounts and secrets

- A Render account connected to the GitHub repository.
- A MongoDB Atlas database. Use a database user with only the permissions required for this application and allow network access only from trusted sources where possible. Render outbound IP allow-listing depends on the selected plan/region; follow the provider's current networking documentation.
- A unique admin email and password (at least 16 characters).
- The exact public application origin as `APP_ORIGIN` (for example, `https://your-service.onrender.com`); use only scheme, host and optional port, with no path or trailing slash.

Never commit `.env`, Atlas credentials, JWT secrets or production admin passwords.

## Deploy

1. Push the repository to a GitHub repository.
2. In Render, create a new Blueprint and select that repository. Render reads `render.yaml`.
3. Add `APP_ORIGIN` using the exact public HTTPS service origin, plus `MONGODB_URI`, `ADMIN_EMAIL` and `ADMIN_PASSWORD`. `JWT_SECRET` is generated by the blueprint; keep it private.
4. Deploy the service. The build command uses the committed npm lockfile with `npm ci`, then builds `frontend/`; the Express server serves `frontend/dist` and the `/api` routes from the same origin.
5. Wait for `/api/health` to return `{"status":"ok"...}`.
6. **Seed the database before opening the store to customers.** The Render Free plan does not provide Shell/SSH or one-off jobs. Run the seed from a trusted local computer instead:
   - Check out the exact deployed commit and install dependencies with `npm ci`.
   - Create a temporary, untracked root `.env` file containing the production `MONGODB_URI`, `ADMIN_EMAIL` and `ADMIN_PASSWORD`. Never paste these values into chat, source files or terminal screenshots.
   - Confirm the URI points to the intended NEXORA database, then run `npm run seed` once.
   - Delete the temporary `.env` file after the command finishes. Do not run the seed again after customers or admins have edited catalogue data: it upserts sample products and categories, including stock and image fields. The seed creates the initial admin only when that email does not already exist; it does not reset an existing admin password.
7. Open the Render service URL. Test customer registration, login, CSRF-protected mutations, cart, COD checkout, order history, admin login, product CRUD and order status transitions.
8. Add a custom domain only after the default service URL and health check work. Update `APP_ORIGIN` to the custom HTTPS origin and redeploy. Enable provider-managed HTTPS.

## Runtime settings

The blueprint sets Node 26.13.1, `NODE_ENV=production`, `TRUST_PROXY=true` and `COOKIE_SAME_SITE=lax`. `APP_ORIGIN` is required at startup and is used to validate the `Origin` header (or `Referer` fallback) on state-changing requests. If you later split frontend and backend across different sites, revisit CORS, `SameSite=None; Secure`, CSRF and browser third-party-cookie behavior rather than copying the current settings blindly.

## Database requirement

Checkout and order cancellation use MongoDB transactions. Use MongoDB Atlas or another replica-set deployment. A standalone local MongoDB server does not support multi-document transactions.

## Costs and availability

Hosting and database plans can change. Review current pricing, sleeping/availability limits, backups and bandwidth before selecting a plan. The Blueprint currently selects Render `free` to avoid creating a paid service without explicit approval. Free services can sleep after inactivity and have resource limits. Confirm current provider pricing and limitations before deployment; do not change to a paid plan without the project owner's approval.

## Deployment acceptance checklist

- [ ] Public URL loads over HTTPS.
- [ ] `APP_ORIGIN` exactly matches the public HTTPS origin.
- [ ] `/api/health` returns 200.
- [ ] Registration/login/logout work; session cookie is HttpOnly and Secure in production.
- [ ] A CSRF-protected POST without a valid token is rejected; a mismatched Origin/Referer is rejected.
- [ ] Non-admin users receive 403 from `/api/admin/*`.
- [ ] Product prices are read from MongoDB, never trusted from browser input.
- [ ] Checkout decrements stock transactionally and rejects insufficient stock.
- [ ] Order cancellation restores stock once; terminal orders cannot be changed.
- [ ] COD order is marked paid only when Admin marks it delivered.
- [ ] Backups and restore procedure are configured.
- [ ] No secrets appear in repository, frontend bundle or logs.

## Alternative deployment: Docker-capable platforms

A root `Dockerfile` is provided for platforms that deploy containers rather than linking a Git provider directly. It builds the React app and runs the Express API from the same origin. The image uses Node 26.13.1 in both stages because `argon2` includes a native module. Configure the same runtime settings listed above (`APP_ORIGIN`, `MONGODB_URI`, `JWT_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`) in the platform's secret manager, and expose the platform-provided `PORT`. Do not bake `.env` files or credentials into the image. MongoDB must still be a replica-set deployment for transactional checkout/cancellation. The container build has not yet been executed in this environment; treat it as an alternative deployment path pending CI verification.

## Verification

The CI workflow performs a clean lockfile-based install (`npm ci`), audits production dependencies for high/critical vulnerabilities, runs the automated tests and builds the frontend. A successful workflow validates those steps only; it does not prove live database transactions, browser end-to-end behavior or deployment readiness.
